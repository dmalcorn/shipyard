# scripts/

Three distinct categories of script live in this directory: **factory-runtime scripts** that the LangGraph invokes during a build, **operator orchestration scripts** that humans run to start a build, and **operator forensic tools** that humans run after a build to analyze what happened. They have nothing to do with each other; the distinction below saves the next investigator from wondering which is which.

## Operator orchestration

Humans run these to start (or wrap) a factory build.

| Script | What it does | When you'd use it |
|---|---|---|
| `preflight.sh` | Stages a target's `factory.yaml` + `.env` into shipyard root, runs auth/import smoke tests, kicks off `python -m src.main --rebuild`, and removes the staged files on exit (success, failure, or Ctrl+C). | Every build kickoff. Lets per-target config live in each target repo and makes interleaved multi-target builds safe. See [docs/how-to-setup-factory-harness.md](../docs/how-to-setup-factory-harness.md). |

## Factory-runtime scripts

The LangGraph invokes these during a rebuild. They must exist and be executable for the factory to work.

| Script | Used by | Purpose |
|---|---|---|
| `ci.sh` | Shipyard's own test suite + 21 references in src/tests/ | Auto-generated CI script for shipyard itself. Lint + typecheck + pytest with `--story` / `--quick` / `--test` flags. **Note:** target projects get their own separate `scripts/ci.sh` generated by the architect agent per [target-templates/ci-script-specification.md](../gauntlet_docs/target-templates/ci-script-specification.md) — that one runs in the target's repo, this one runs in shipyard's. |
| `local_ci.sh` | Human developers committing to shipyard | Pre-commit utility — runs ruff + mypy + pytest in sequence. The README at [README.md#run-tests](../README.md#run-tests) tells contributors to invoke this before commits. |

## Operator forensic tools

These are run by humans (operator + Claude when authed) **after** a build to analyze what happened. None of them are invoked by the running LangGraph.

| Script | What it does | When you'd use it |
|---|---|---|
| `extract_log.py` | Pulls a relay session's events as a JSON dump (full or incremental) | Archiving a build's events for offline analysis. Documented end-to-end in [How-to-extract-db-logs.md](../gauntlet_docs/How-to-extract-db-logs.md). |
| `log_analysis/cost_by_story.py` | Per-story cost breakdown from a JSON dump | Spotting expensive stories, comparing runs |
| `log_analysis/failure_patterns.py` | Stories that needed >1 CI cycle, gave up, or stalled | Diagnosing fix_ci tuning |
| `log_analysis/phase_durations.py` | Where wall-clock time went per story | Capacity planning, spotting unusual phase ratios |
| `log_analysis/auth_halt_check.py` | Did rate-limit / auth-failure messages appear? Did halt detection fire? | Validating commit `d88ce0d`, finding new Anthropic auth-message variants |

The four `log_analysis/*.py` tools all consume the JSON output of `extract_log.py`. See [scripts/log_analysis/README.md](log_analysis/README.md) for the workflow and per-script details.

## How to know if a script is factory-runtime or operator-only

Grep `src/` and `tests/` for the script name. If anything in source code references it, it's factory-runtime. If only docs reference it, it's an operator tool.

```bash
grep -rn "<script-name>" src/ tests/ --include="*.py"
```

This grep is the canonical answer to "is this dead code?" — when src/ + tests/ shows zero references and only docs cite the script, you're looking at an operator-driven utility, not a LangGraph dependency.
